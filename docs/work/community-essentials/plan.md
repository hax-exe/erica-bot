## Deviations
- T1: the migration is `drizzle/0004_reflective_brother_voodoo.sql` (8 CREATE TABLE, 13 ADD COLUMN, 2 CREATE INDEX). Migrations 0000 to 0003 and their snapshots are byte-identical.
- T1: `scripts/migrate-sqlite-to-mysql.ts` changed. It now copies only columns that exist in both the SQLite and the MySQL table, so the new NOT NULL columns (module toggles, phishing, boost) take their MySQL defaults instead of failing on NULL. `verification` stays in `SKIPPED_COLUMNS`: in old SQLite data it belongs to the retired Minecraft module (default on), and copying it would switch the opt-in Member Verification module on.
- T1: the schema also exports `LevelMultiplierTargetType` (`'role' | 'channel'`) and `AnnouncementPingType` (`'r' | 'u'`) for the `$type<>` columns. There is no index on `scheduled_announcements` because the spec lists none.
- T3: `RolePersistUtil.ts` loads `./database.js` lazily (`getDb()`), because database.ts needs `DATABASE_URL` and migrates on import, so the pure helpers and their test run without it (CI has no database). The pure helpers are `filterRestorableRoleIds`, `filterSavableRoleIds` and `formatRoleList`.
- T3: a snapshot with no roles is still saved when `restore_nickname` is on and the member had a nickname; otherwise "nothing to save" deletes it. The snapshot is deleted after every restore attempt, also when an API call failed. The "Roles Restored" log is skipped when the `logging` module is off, like the other member logs, and adds Skipped/Left/Nickname fields. `/rolepersist` config subcommands append the `/module enable` hint when the module is off, and `ignore-add`/`ignore-remove` also prune deleted roles from the ignore list.
- T6: `LevelingUtil.test.ts` stubs `./database.js` with `mock.module` and imports `LevelingUtil` dynamically, because `LevelingUtil.ts` imports database.ts statically (needs `DATABASE_URL`, migrates on import; CI has no database). `getXpMultiplier` takes the thread's parent channel as a fifth argument `parentChannelId`; a channel's own multiplier wins over its parent's. Voice XP uses the channel the time was spent in, and the boost is checked when the XP is awarded. `set-channel` is limited to text, announcement, voice, stage, forum and media channels. Removed one stale `biome-ignore` in `voiceStateUpdate.ts`.
- T5: the rule is evaluated first of all checks after the exemptions (before new-account and spam), not only before the word filter. Besides `https?://` URLs it also matches scheme-less domains (`discord-gift.xyz/claim`), since Discord links those too; `PhishingUtil.ts` has no database or discord.js imports. `refreshPhishingList()` never throws: it returns `{ ok, size | error }`, the listener logs the warning, and a download with no valid domains also counts as a failure (previous list kept). List entries are normalised and junk dropped (the live list loads as 36,683 of 36,749 entries). The hit reason wraps the domain in backticks (`Message contained a known scam link (`domain`)`) so it is not a clickable link in the DM and mod log. `/automod configure` needed no logic change: for `phishing` the existing "nothing to update" message already lists only `action` and `timeout-minutes`. `.env.example` has a new `PHISHING_LIST_URL=` section (T9 does not need to add it).
- T8: `HighlightUtil.ts` loads `./database.js` lazily (`getDb()`), like T3, so `findHighlightMatches` and the other pure helpers are testable without `DATABASE_URL`. Whole-word matching uses Unicode lookarounds (`(?<![\p{L}\p{N}_])...(?!...)`) on the lowercased message instead of `\b`, so keywords such as `c++` or `.net` work. The bot-blacklist check covers the author as well as each recipient. In a private thread a recipient must also be a thread member or hold Manage Threads (so a DM never leaks a private thread). The DM payload uses `MessageFlags.IsComponentsV2` directly because `CV2_FLAG` is typed as the whole `MessageFlags` enum and does not fit `member.send()`.
- T2: `VerificationUtil.test.ts` stubs `./database.js` with `mock.module` (real schema, same approach as T6) and imports the util dynamically, because `VerificationUtil.ts` imports database.ts statically. Besides `generateCaptchaCode` it also tests `renderCaptcha` (PNG), the pending-code store (3 attempts, 5 min TTL) and `isAccountOldEnough`. `/verification setup` is a patch: omitted options keep their stored value, so the unverified role cannot be cleared through it (disable the module instead); it also requires the bot to have Manage Roles and the two roles to differ. The `verification:code` button replies with an ephemeral error instead of the modal when no code is pending (still a single response). The "Verification Blocked" / "Member Verified" logs are skipped when the `logging` module is off, like the other member logs. All three interactions live in one listener (`interactionCreate.ts`, exact custom-ID matches, blacklist check after the match). Cross-feature note: the rejoin interplay with role persistence is handled in R1 (below).
- T4: the pure helpers (`isFakeAccount`, `countInviteRows`, `selectRewardRoleIds`) live in `InviteUtil.ts` and the test is `src/lib/InviteUtil.test.ts` (it also covers `getJoinInvite` memoization), not `InviteTrackingUtil.test.ts`: `InviteTrackingUtil.ts` imports `./database.js` (needs `DATABASE_URL`, CI has none). The invites listener runs `getJoinInvite` for every non-bot join before checking the `inviteTracking` module, so the invite cache keeps up with use counts even when both Invite Tracking and Logging are off. `recordInviteJoin` first closes (`left_at` = now) any still-open row of that user, for a leave missed while the bot was offline. `/invites` replies, the leaderboard included, are ephemeral; its Previous/Next buttons use `invites:lb:<page>` handled by `src/listeners/invites/leaderboardPagination.ts` (the shared `page:` listener was not touched). The leaderboard lists inviters with at least one effective invite, 10 per page. `reward-add` requires the role to be assignable by the bot (not `@everyone`, not managed, below the bot's highest role, bot has Manage Roles); R1 later added the invoker and dangerous-permission checks (see R1). `guildInviteCreate.ts` / `guildInviteDelete.ts` needed no change.
- T7: `AnnouncementUtil.ts` has no database import (unit tests run without `DATABASE_URL`); the active-count query is repeated in `schedule.ts` and `scheduleModal.ts`. It also exports `ANNOUNCE_COLOR_CHOICES` (used by `/mod announce` and `/schedule create`, same names and order) and `buildAnnouncementModal` (the `/mod announce` modal JSON is byte-identical). Added beyond the spec: `every` is capped at 365 days (bigint overflow guard); the schedule modal caps the body at 3800 chars (CV2 4000-char text limit, so a schedule can never fail to send for length); the modal submit also re-checks the ping rule, the channel, the 25 limit and rejects a blank body; one pending form per user (a new `/schedule create` replaces the old nonce); `in` is measured from the modal submit. The scheduler keeps in-memory per-run progress so a retry after a failed container send or a failed DB update never repeats the ping or the post. `/schedule delete` deletes any row of the guild (active or finished); `id` autocomplete is gated on Manage Server.
- R3: bot access at creation needs View Channel plus Send Messages, or Send Messages in Threads instead of Send Messages for a thread (Discord does not honour Send Messages inside threads), checked in `schedule.ts` and `scheduleModal.ts` through `botPostPermissionError` in `AnnouncementUtil.ts`. At send time the scheduler fetches the creator and applies `checkScheduleAuthority`: creator gone or without Manage Server deactivates the schedule; losing only the ping permission sends the announcement without the ping. Every deactivation (undeliverable errors, channel gone, creator check) is logged through `sendLog` + `logContainer` while the `logging` module is on, only when the guarded update really changed the row; a dropped ping is logged once per run (a recurring schedule logs it on each run). A transient creator-fetch failure is retried on the next tick.
- R2: new limits beyond the spec: at most 10 DMs per message (the cap counts DM attempts after the eligibility checks, so members who cannot read the channel do not use up slots; candidates keep keyword match order), at most 5 highlight DMs per member per 10 minutes across channels and servers (keyed by user, spent before the send and refunded when it fails), and no DMs for messages with a known scam domain (`findPhishingDomain` with an empty whitelist, skipped silently). On 40003 the message stops, the recipient's channel mark is cleared so a later message retries, and all highlight DMs pause for 60 s (one warning per pause); 50007 keeps the channel mark and spends no budget; other failures keep the mark, refund the budget and log a warning. The `/highlight add` reply states the limits. `FEATURES.md` lists the new limits.
- R2 (follow-up): at most 30 candidates per message get the eligibility check (member lookup, permissions, blacklist); a `guild.members.fetch` failing with 10007 caches the miss for 10 minutes per guild and user (`markMemberMissing` / `isMemberMissing`, filtered out of the candidates before they use a check slot), so departed subscribers cost one API call per 10 minutes instead of one per message. The miss is cached, not deleted: the highlight rows of departed members stay in the table.
- R1: role persistence restores with one PUT per role (`guild.members.addRole`), not the single `roles.add(..., 'Role persistence')` call in spec section 2: an array `roles.add` is a full-replace PATCH built from the cached roles and can drop roles that autoroles or the verification listener add on the same join. Errors are logged per role and failed roles count as skipped. Invite rewards are granted one PUT per role too, for the same reason.
- R1: `src/lib/RoleSafety.ts` (no database import) replaces `roleAssignmentProblem` (VerificationUtil) and `rewardRoleError` (InviteTrackingUtil). At configuration time (`/verification setup` roles, `/invitesadmin reward-add`) it refuses @everyone, managed roles, roles at or above the bot or the invoker (guild owner exempt from the invoker check) and roles with Administrator, Manage Server, Manage Roles, Manage Channels, Manage Webhooks, Ban/Kick/Timeout Members or Mention Everyone, and still requires the bot to have Manage Roles. It does not require the invoker to have Manage Roles (the commands stay Manage Server). Two different roles on the same position count as "at" (stricter than Discord's ID tie-break). At grant time (verified role, unverified role on join, invite rewards, restored roles) only @everyone, managed, bot hierarchy and the permission list are checked; an unsafe verified role gives the member an error naming `/verification setup`, the others are skipped with a warning log. `filterRestorableRoleIds` now takes RoleSafety's `RoleFacts` (`permissions` bitfield instead of `administrator`) and `botHighestRole` instead of `botHighestPosition`.
- R1: the verification join listener skips the unverified role when the member already holds the verified role or when Role Persistence is on and `snapshotRestoresRole` (new, RolePersistUtil) says the snapshot would give the verified role back (saved, not ignored, still safe to grant, bot has Manage Roles); if the snapshot read fails it adds the unverified role. The already-verified replies of the Verify button and the code modal remove a leftover unverified role and say so (error with the staff hint if removal fails). `/invitesadmin` dropped its own Manage Server check, now covered by `requiredUserPermissions` + `Moderation`. `getJoinInvite` memoizes per `guildId:userId:joinedTimestamp`.
